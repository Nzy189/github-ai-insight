# 报告页信息架构改造 — 设计文档

> 日期: 2026-08-12
> 状态: 已确认，待实施
> 影响文件: `ai_analyzer.py` · `models.py` · `templates/report.html.j2` · `report_generator.py` · `DESIGN.md` · `tests/`

---

## 1. 问题

用户看完第一份真实报告（`guillaumemeyer/watermarks-remover`）的原话：

> 我现在看这个 感觉也没看明白有什么核心卖点 或者甚至不太理解这个用来干啥

追问后明确了读者场景与目标：**在手机上（企微内置浏览器）点开，决定要不要现在去装来用**。要求是"言简意赅地告诉我它解决什么问题、值不值得花时间"。

### 实测到的病灶

对线上报告量取的真实数值（375px 视口，页面总高 2775px，首屏 812px）：

| 顶部 Y | 区块 | 高度 |
|---|---|---|
| 108 | HERO | 276 |
| 432 | 评分详情 | 309 |
| 789 | 快速上手 | 269 |
| 1106 | 详细介绍 | 609 |
| 1763 | 技术亮点 | 245 |
| 2055 | 仓库信息 | 492 |

四个具体缺陷：

1. **"这是什么"只有一行 22px 的字**，上压 36px 的仓库名、下顶 80px 的评分环，视觉上不是主角
2. **评分排第二位**（Y=432，占 309px）—— 读者还不认识这个项目，先收到 4 个数字。评分是对某物的评判，可读者尚未理解那个"某物"
3. **H1 是仓库名**（`watermarks-remover`），对陌生项目信息量近乎为零，却占着最大字号
4. **最可扫描的技术亮点在 Y=1763**，要滚过两屏才看到；609px 的长文反而排在它前面

第五个缺陷不在布局，在内容：`one_liner` 产出的是名词堆叠——"多供应商AI水印移除工具，清理文本与文件元数据以保护隐私"——没有场景，读者无法代入。**光改模板改不出效果。**

### 根因

现有信息架构按**系统的逻辑**排列（先评分 → 再结论 → 后详情），而读者按**自己的问题**阅读：

```
解决我什么问题 → 怎么解决的 → 我装得上吗 → 值不值得
```

当前报告的回答顺序正好是倒的。

## 2. 方案选择过程

在可视化伴侣中用真实数据、按 320px 真机宽度做了三轮对比：

**第一轮 · 首屏结构**（A 三问名片 / B 人话当大标题 / C 顶部加 TL;DR）→ **选 B**，理由是结论上位、仓库名降级。

**第二轮 · B 的三要素排法**（B1 三栏横排 / B2 纵向标签行 / B3 砍到两块）→ **选 B2**。
B1 存在硬伤：320px 屏幕上每栏仅 93px，中文一行放不下 5 个字，标签 9px 低于 DESIGN.md 的 Nano 下限（11px）。
B3 把痛点押进大标题，对 LLM 每日自动生成、质量不完全可控的内容而言风险过高。
B2 吸收了 A 方案最有价值的特性——**带标签，不必猜哪句回答哪个问题**——同时保住大标题的 C 位。

**第三轮 · 首屏以下顺序**（1 由浅入深 / 2 先给证据 / 3 由浅入深+评分压扁）→ **选 3**。

**第四轮 · 内容来源**（新增 tldr 嵌套字段 / 三个平级字段 / 从正文拆）→ **选 tldr 嵌套字段**。

## 3. 目标结构

```
Hero      one_liner 当大标题（手机 21px / 桌面 26px / 700）
          仓库名降为等宽小字副标题 + ★ Star + 语言
          tldr 三行标签卡（左标签列宽 52px / 标签字号 11px / 右内容 13px）
          判断条：评分环 52px + 「值得试 · 入门友好」+ rating_reason
          [前往 GitHub ↗]
──────── 手机首屏边界 ────────
技术亮点   3 条 bullet + 「适合谁」一行  ← 30 秒
详细介绍   4 段口语化正文               ← 3 分钟
评分依据   四行横向细条                 ← 存疑才查
仓库信息   表格
Footer
```

标签字号取 11px 而非 10px：DESIGN.md 的 Nano 层级下限就是 11px，而本次否掉 B1 方案的理由之一正是它的 9px 标签越界，不能自己再犯。

排序原则：**按读者愿意付出的时间递增**。

评分区降级的理由：总分与「值得试」已在首屏交代完毕，此区块唯一剩余作用是"给你看我怎么算的"，不应再占 309px 和整屏。压成四行细条后约 90px，且权重与分数左右对齐成一条扫描线，比 2×2 网格更利于比较。

## 4. 数据契约变更

### 4.1 新增 `tldr`

```json
{
  "one_liner": "AI 写的东西会被偷偷打上隐形标记 —— 这工具帮你洗干净",
  "tldr": {
    "pain":     "平台已经能检测出你的稿子是 AI 写的",
    "solution": "三层清理：隐形 Unicode 字符、统计型文本水印、C2PA / EXIF 元数据",
    "fit":      "纯 Python 标准库，不用 Docker，NAS 直接跑"
  },
  "highlights": ["…", "…", "…"],
  "target_audience": "…",
  "difficulty": "low",
  "rating": 4,
  "rating_reason": "…",
  "detailed_intro": "…",
  "scores": { "utility": 75, "problem_solving": 85, "popularity": 80, "nas_usability": 90 }
}
```

`models.py` 新增：

```python
@dataclass(slots=True)
class Tldr:
    pain: str = ""
    solution: str = ""
    fit: str = ""
```

挂在 `Analysis.tldr`，默认 `Tldr()`。`Analysis.as_dict()` 一并输出。

### 4.2 Prompt 变更

**`one_liner` 从软要求改为硬约束**：

- 必须是完整句子，带使用场景
- 禁止名词短语堆叠（明确给出反面示例："多供应商AI水印移除工具，清理文本与文件元数据以保护隐私"）
- 30 字以内
- 读者读完应能复述"这东西干嘛的"

**`tldr` 三句各 ≤40 字**：

- `pain` — 不用它会怎样，要具体场景，不是抽象名词
- `solution` — 它具体干了什么，讲人话，不罗列 API
- `fit` — **必须包含具体部署事实**：依赖、内存占用、要不要 Docker、要不要显卡。禁止"适合自托管用户"这类无信息量表述

### 4.3 字段级降级

`tldr` 缺失或部分缺失时**逐字段兜底，不整体降级** —— 模型少给一个字段不应毁掉整页。

`normalize_analysis` 中：

| 字段 | 缺失时回退 |
|---|---|
| `pain` | `repo.description`，仍为空则留空（模板隐藏该行） |
| `solution` | `repo.description`，仍为空则留空 |
| `fit` | 由 `repo.topics` 推断：含 `docker` → "仓库标注了 Docker 支持"；否则留空 |

LLM 完全不可用（`build_degraded_analysis`）时：

| 字段 | 值 |
|---|---|
| `pain` | `repo.description` 或 "该仓库未填写描述" |
| `solution` | "主语言 {language}，Topics: {前 3 个}" |
| `fit` | "AI 分析不可用，部署要求请查看仓库 README" |

`fit` 的降级文案刻意保持诚实，不编造部署结论。

## 5. 模板变更

`templates/report.html.j2`：

1. **Hero 重构** — `one_liner` 升为 `<h1>`；仓库名降为等宽副标题；新增 tldr 三行标签卡；`快速上手` 区块整体上移并压缩成一条判断条（评分环 52px + 徽章 + `rating_reason`）
2. **区块重排** — 技术亮点 → 详细介绍 → 评分依据 → 仓库信息
3. **评分区改造** — 2×2 卡片网格改为四行横向细条：`维度名(52px) | 进度条(flex) | 分数(右对齐)`，权重并入维度名
4. **`适合谁`（`target_audience`）** — 从原「快速上手」卡移入「技术亮点」区块下方，作为一行补充说明

响应式：判断条在 <640px 下保持横向（评分环 + 文字），tldr 标签列固定 52px 不缩。

### 与 DESIGN.md 的偏离

三处需同步更新 `DESIGN.md`：

| 项 | 原规范 | 新规范 | 理由 |
|---|---|---|---|
| Hero 标题 | Display 36px / 700，内容为项目名 | 21px（手机）/ 26px（桌面）/ 700，内容为一句话价值 | 36px 放长句在 375px 屏上会占掉近半屏 |
| 评分区 | §4 评分卡片 2×2 网格 | 四行横向细条 | 评分已降级为佐证，不应占整屏 |
| 评分环 | §4 80px（手机 64px），Hero 居中独立元素 | 52px，并入判断条左侧 | 总分已不是首屏主角，让位给一句话价值 |

其余色彩、间距、阴影、字体、圆角规范全部沿用，不变。字号一律不得低于 Nano 层级的 11px。

## 6. 测试

新增用例：

**数据层**
- `tldr` 完整 / 完全缺失 / 部分缺失（仅 pain）/ 类型错误（字符串而非对象）→ 均能规整为 `Tldr`
- 字段级回退：`pain` 缺失时取 `repo.description`
- `fit` 由 topics 含 `docker` 推断
- `build_degraded_analysis` 产出三个字段且 `fit` 不编造部署结论
- 旧数据（JSON 中无 `tldr` 键）不抛异常

**模板层**
- tldr 三行全部渲染，且各行标签文案正确
- 某行内容为空时该行不渲染（不留空壳）
- `one_liner` 出现在 `<h1>` 内，仓库名不在 `<h1>` 内
- 区块出现顺序为：技术亮点 → 详细介绍 → 评分依据 → 仓库信息
- 评分细条四行，宽度百分比与分数一致
- `target_audience` 出现在技术亮点区块内，不在判断条内
- 自包含性回归：无外部请求、无 `<script>`
- XSS：`tldr` 各字段经 autoescape

**渲染层（浏览器实测）**
- 320px 与 375px 下无横向滚动
- 首屏（812px 内）能看到：大标题、tldr 三行、判断条
- 所有字号 ≥ 11px（DESIGN.md Nano 下限）
- CTA 触摸目标 ≥ 44px

## 7. 不做的事

- **不回溯重渲染历史报告**。`data/reports/` 里的旧 HTML 保持原样，数据库旧记录不迁移。
- **不改评分权重**。`SCORE_WEIGHTS` 维持 35/30/25/10。
- **不改企微推送消息格式**。本次只动 HTML 报告页；推送消息的改造如有需要另开一轮。
- **不加交互**。报告页保持零 JS、自包含，不引入折叠面板或标签页。
